03 / LINUX INFRASTRUCTURE + AUTOMATION

50 workstations.
One defined baseline.

How I gave aging hardware a useful second life with Lubuntu—and turned a working desktop configuration into an Ansible-managed deployment process.

Project context: AnsibleKing, the workstation standardization initiative.

The goal was not simply to install Linux. It was to make the next workstation predictable.

At ECA Direct, aging Windows workstations were struggling with ordinary agent work. Replacing the fleet was one possible answer, but I first investigated whether a lighter operating system could make the existing machines useful again. The resulting project standardized 50 workstations on Lubuntu, then used Ansible to apply the configuration needed for daily operations. [S1]

I owned the research, baseline definition, playbook development, testing, documentation, and rollout. The useful outcome was not just a different desktop: it was a defined setup that could be applied to a fresh installation instead of recreated from memory.

01 / THE PROBLEM

Keep the hardware.
Change how it is managed.

The business needed usable agent endpoints: a browser, a softphone, employee access, and the settings that made those tools practical. The existing machines were a poor fit for the demands of their Windows environment, but that did not automatically make the hardware unusable.

I selected Lubuntu as the lighter platform for this workload. That solved only part of the problem. Installing a new operating system on 50 computers still leaves 50 opportunities to miss a package, apply a setting differently, or discover an access problem when someone needs to work.

I treated the work as two related changes: refresh the operating system, then standardize the configuration. All 50 machines received fresh Lubuntu installations. Ansible ran afterward; it did not perform the original bare-metal OS installation. Keeping that boundary clear matters when describing what the automation actually accomplished. [S1]

02 / BASELINE DESIGN

Make one workstation understandable before making fifty alike.

I started by creating and documenting a reference workstation. Its purpose was to establish what a usable agent desktop needed, not to produce a disk image to clone indiscriminately. I identified the required software, domain integration, browser and session settings, and the separation between an ordinary employee account and local administrative access.

That baseline became the specification for the playbooks. Instead of treating “looks like the working computer” as the acceptance criterion, I could point to the components and settings that made up the intended state. The same reference also gave troubleshooting a starting point when an endpoint behaved differently. [S1]

03 / CONFIGURATION AS CODE

Turn the setup procedure into something executable.

I used Ansible playbooks to express the repeatable setup, including APT-based package installation and the supporting configuration. The administration workflow used Windows/WSL, SSH, YAML, an inventory, and Git-managed project files. A later infrastructure handover corroborates that controller and inventory arrangement; it is supporting context, not a transcript of the original 50-machine run. [S1] [S3]

Ansible fit a task in which the same configuration needed to reach multiple Linux hosts. Its playbooks can target defined hosts and groups and organize configuration steps in order. Using the apt module let package tasks describe the desired installed state rather than depend entirely on a sequence of interactive commands. [R1] [R2]

The engineering value came from moving configuration out of an administrator's memory and into an explicit, reviewable process. It also made the work easier to explain: which machines were targeted, which step was responsible for a change, and which part needed attention when a host did not finish as expected.

04 / IDENTITY AND RECOVERY ACCESS

A configured desktop still needs a usable login.

The workstation design included domain access for ordinary employees and a designated local account for administration and recovery. I installed domain-related components including realmd, SSSD, and Winbind and configured short-name login so a user could sign in without typing a fully qualified account name. [S2]

That list describes the components in this deployment, not a universal requirement to run every identity component together. The retained account does not establish the exact active authentication-provider path, so I do not present a speculative PAM or SSSD configuration as the original implementation.

I tested several domain accounts and the designated local administrator. I created the local administrative account before restricting root login, then confirmed a root login attempt failed. Those checks established specific behavior: employee access worked for the tested accounts, the local administrative path worked, and the tested root login was rejected. They were not a complete authentication audit. [S2]

Package presence tells me a component exists. A successful login tells me something about whether the person can actually use the workstation.

05 / VALIDATION

Rebuild the workstation, not just the explanation.

My key repeatability test was to wipe a test workstation, start again with a fresh installation, and apply the documented deployment. That challenged an easy assumption: that the reference machine worked because of the playbook, rather than because of a manual change I had forgotten to document. The clean-install validation supported using the process across the fleet. [S1]

I also used a validation playbook to check the required components and installed packages, including the domain-related setup and Zoiper. I kept that automated result separate from the account tests. A “healthy” result from a presence check is not a substitute for successful user authentication or an end-to-end softphone call.

Reported checkWhat it supportedWhat it did not establish

Repeatable deployment is not the same as proven idempotence.

I did not establish a complete second-run test of the original playbooks against an already-configured machine. That is a different test from successfully configuring a fresh installation. Ansible supports idempotent behavior in many modules, but not every module or playbook automatically has it. A repeat-run test with recorded changes would be an improvement to the test suite, not a result I can retroactively claim. [S1] [R1]

06 / PRODUCTION ROLLOUT

Handle the exceptions without losing the baseline.

After validating the reference deployment, I documented the process and applied the playbooks across the 50-workstation rollout. The deployment was not entirely free of exceptions: some endpoints failed their domain-join step. I targeted the affected workstations individually and reran that task; those retries succeeded. [S1] [S2]

I suspected directory-server congestion, but the original error messages and measurements were not retained in the account available for this case study. A successful retry established recovery, not the root cause. It also does not mean all 50 join operations ran at the same instant.

The practical lesson was to make failures addressable. A shared configuration did not require treating every workstation as one indivisible job. I could identify the machines needing attention, narrow the action to the failed step, and check access again without describing the entire deployment as a failure.

07 / RESULTS

A usable fleet, and a process worth keeping.

The project standardized 50 workstations on a lighter Linux platform and kept the existing hardware useful, avoiding the immediate need for a fleet-wide replacement. More importantly for ongoing administration, I had a documented configuration and an automated way to apply it. That replaced repeated setup decisions with a defined baseline. [S1]

The strongest outcome is operational rather than a fabricated performance percentage: the machines remained usable for their intended role, the configuration process was made repeatable from a clean install, and specific access behavior was tested. I do not claim a measured dollar saving, a timed per-device deployment improvement, zero downtime, or complete security compliance from this work.

A stronger next iteration would retain per-host run summaries, explicitly test a second pass on an already-configured workstation, and expand workflow-level validation beyond component presence. Those are clearly identified improvements to the engineering process—not prerequisites being rewritten as completed achievements.

This is the work I want the portfolio to show: understanding the workload, choosing a practical platform, turning configuration into code, testing the assumptions, and dealing with real deployment exceptions without overstating the evidence.
