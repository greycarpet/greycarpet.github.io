ECA Reporting Hub
A production reporting initiative, not a template dashboard.

The real task was not exporting data. It was making the reporting rules explicit.

At ECA Direct, recurring client reports involved more than running a query. Someone had to obtain the right inputs, apply project-specific rules, reconcile the result, and put it into the required format. Important decisions lived inside the manual workflow rather than in one clear specification.

I mapped those decisions and used Python and SQL to make the process repeatable. The work grew across 32 reporting workflows, developed into ECA Reporting Hub, and later moved into a Dockerized application on Linux. The result was faster reporting, but the more durable improvement was a process that could be inspected, corrected, and used repeatedly. [S1]

01 / THE OPERATING PROBLEM

Reports depended on people reconstructing the process.

The starting environment combined Access, SQL, Python, source-system data, and client files. VICIdial supplied calling activity; LimeSurvey supplied survey responses. Producing a usable deliverable meant relating those sources, interpreting their fields, and following the rules for the specific project. [S1]

Two reports could look similar while requiring different record selections, response mappings, or calculations. Automating only the file export would have left the difficult part untouched. I needed to understand which records belonged in a result, why a record was excluded, and how the final figures were calculated.

I started with the existing reporting work rather than designing a generic dashboard first. I documented the inputs and decisions, converted repeatable steps into code, and compared the generated deliverables with known or manually prepared outputs. That comparison helped separate a coding error from an incomplete understanding of the business rule.

BEFORE

02 / BUSINESS LOGIC AS ENGINEERING

One pipeline does not mean one rule for every project.

The automation combined extraction, joins, filtering, deduplication, response translation, calculations, formatting, and validation. SQL handled relational selection and transformations; Python coordinated processing and output generation. I kept the project's meaning central: reusing a processing pattern was useful, but silently imposing the same reporting rules on different clients was not. [S1]

For example, a call attempt and a new reportable outcome are not the same thing. In one monthly reporting workflow, an unchanged finalized response could reappear after a later callback. The correct behavior was to suppress that repeated return while retaining response changes and preserving call totals. A blanket “remove duplicate people” rule would not express those requirements. [S3]

DecisionEngineering questionWhy it matters
Record selectionWhich project, period, and population does this output describe?Correct data from the wrong scope is still an incorrect report.
Repeated outcomesIs this a new response, a changed response, or an unchanged repeat?A new call does not necessarily justify another client return.
CalculationsDo the time basis and numerator represent the same activity?A plausible rate can still be based on the wrong denominator.
Output contractAre the fields, mappings, layout, and totals what the recipient expects?A generated file must preserve meaning, not merely open successfully.

These questions made the work maintainable. When a discrepancy appeared, there was a specific rule or transformation to investigate instead of an opaque sequence of manual edits.

03 / FROM SCRIPTS TO AN APPLICATION

Make the automation usable beyond the person who wrote it.

Individual scripts were a useful first step, but they were not the end product. As the number of workflows grew, I brought the reporting tools together in ECA Reporting Hub. The desktop application provided a common place to run project reports rather than treating each script as a separate administrative task. [S1]

The next stage was a hosted application. That required rethinking how reporting data was sourced and stored, not simply placing the desktop executable in a container. The documented design used controlled, read-only ingestion from the calling and survey systems into a dedicated reporting datastore, with reusable project workflows and scheduled synchronization. [S1]

This was an evolution of working tools, not a claim that all 32 workflows reached the same web-production state at once. Each project's business rules and acceptance checks still mattered. A successful platform deployment did not automatically authorize every generated file for client delivery.

04 / LINUX PLATFORM OPERATIONS

The application needed an operating model, not just an image.

The hosted stack used five Docker Compose services: a Django web application served by Gunicorn, a Celery worker, Celery Beat, PostgreSQL, and Redis. The application services shared an image but ran different commands. The documented deployment kept database state and working files outside the replaceable application containers through named volumes and bind mounts. [S2]

I treated updates as controlled changes to an operating service. In the October 6 deployment records, the previous source and application image were preserved, a candidate image was built and checked, application services were recreated, and readiness and report behavior were checked again. PostgreSQL and Redis remained running during that particular update. [S2] [S3]

The distinctions mattered. A running container was not enough to accept a reporting change. Preserved volumes made data independent of a container's lifecycle, but they were not a completed backup-restore test. Docker provided packaging and service separation; it did not, by itself, produce the earlier reporting speedup. [R2]

05 / VALIDATION IN PRODUCTION MAINTENANCE

Prove the change—and check what should not change.

Automation did not eliminate the need to investigate bad results. It gave me a better way to make the expected behavior explicit and test a correction. Two October 6 changes show the difference between accepting an application that starts and accepting a report that remains correct.

Repairing a time calculation without changing unrelated results.

An agent-hours repair addressed staffed-time calculation and completeness of campaign activity mirroring. The candidate was checked against the baseline within a shared repeatable-read database snapshot. That comparison limited the risk of confusing a real calculation change with source data changing between tests. PostgreSQL repeatable-read transactions provide a stable snapshot for successive reads within the transaction. [S4] [R3]

The repair record reports preserved count/list totals, source-time agreement, and Excel parity for the checked filters. It also states that the source databases and client report files were not modified. That gave the result more meaning than simply observing a successful image build.

Suppressing an unchanged return without suppressing new information.

A second repair changed the monthly rule for previously reported, unchanged finalized responses. I validated it through preflight, candidate-image, and live stages. The deployed check suppressed an unchanged repeat while reporting preservation of response-change behavior and existing official files. Call totals and retained output cells were checked separately. [S3]

The broader lesson was to test both sides of a correction: what must change and what must remain the same. In reporting, an apparently successful fix can be wrong if it also changes a total, removes a legitimate response, or rewrites a previously published file.

06 / MEASURED AND REPORTED OUTCOMES

Give the time back.
Keep the measurements honest.

The historical reporting account described 32 workflows and a combined cycle that fell from roughly eight hours to less than 30 minutes. Separately, individual automated deliverables that had taken 15 minutes to two hours were reported completing in under five seconds. Those are different measurements: a combined reporting cycle is not the same as one report's execution time. [S5]

The practical benefit was less time reconstructing and executing routine reporting steps, with more time available for exceptions, oversight, and other engineering work. The platform also made it easier to discuss the source of a number: an input, selection rule, calculation, and output could be investigated as separate parts of the process.

I keep the speed claims attached to their original scope. They do not promise that every sync, dashboard, export, or future client workflow finishes in seconds, and they should not be attributed to containerization alone.

07 / OWNERSHIP AND LESSONS

The engineering responsibility stayed with me.

I used AI assistance extensively during development. My ownership was in understanding the operating problem, supplying the workflow context, specifying the business rules, reviewing proposed changes, executing deployments, and validating the resulting behavior. I do not present the project as unaided manual authorship of every line of code. [S1]

That made verification more important, not less. A convincing implementation still had to match the approved reporting behavior. A comparison against known outputs, a same-snapshot check, or a regression test that preserved unrelated totals carried more weight than an explanation that merely sounded correct.

A fast report is useful only when the meaning survives the automation.

ECA Reporting Hub demonstrates the connection between software and infrastructure work: discover the rules, build usable automation, separate application services from persistent data, and validate changes in the environment where people depend on the result. It is an implemented platform that continued to evolve—not a finished claim that every workflow, restore scenario, and publication path had been exhaustively tested.
